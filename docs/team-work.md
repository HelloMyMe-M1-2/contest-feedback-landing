# 팀 협업 안내

## 어디에서 작업하나요?

이 저장소는 프로젝트의 코드와 기록을 모으는 곳입니다. `main`은 팀이 함께 확인하는 기준 버전입니다. 팀 전달 시안을 바탕으로 한 테스트 화면이 공개되어 있으며, 실제 데이터 수집은 아직 준비 중입니다.

GitHub 저장소와 [테스트 화면](https://contest-feedback-landing.pages.dev/)은 공개되어 누구나 볼 수 있습니다. 저장소에 직접 변경 사항을 올리려면 별도 권한이 필요합니다. 현재 `main`에 푸시하면 Cloudflare가 공개 테스트 화면을 자동으로 다시 배포합니다.

## 개발자가 아닌 팀원은 무엇을 하나요?

코드를 직접 수정하거나 터미널을 실행할 필요는 없습니다. 실험 목적, 피드백 예시, 화면 디자인과 문구가 팀의 의도에 맞는지 확인하고 의견을 전달하면 됩니다. GitHub 문서를 볼 수 있다면 관련 부분을 확인하거나 의견을 남길 수 있고, 익숙하지 않다면 개발자에게 평소 사용하는 소통 방식으로 전달해도 됩니다.

현재 화면은 팀이 전달한 시안을 기반으로 합니다. 변경 의견은 담당자와 논의합니다. 팀원 초대와 접근 권한은 담당자가 따로 관리합니다.

## 변경 사항을 반영하는 방법

팀 운영을 위한 권장 절차입니다. GitHub 설정으로 자동 강제되는 규칙은 아닙니다.

1. 개발자는 `main`을 기준으로 `feature/` 또는 `fix/`로 시작하는 작업 브랜치를 만듭니다. 예: `feature/posthog-test`.
2. 변경 목적과 실제로 달라지는 점을 정리합니다. 이벤트 기준이 바뀌면 `docs/events.md`를 함께 고칩니다.
3. 가능한 경우 `npm test`와 `npm run build`를 실행하고, 결과 또는 실행하지 못한 이유를 기록합니다.
4. GitHub에 변경 사항을 올리고 Pull Request(PR)를 만듭니다. PR은 변경 내용을 팀이 확인하고 기준 버전에 합치기 위한 요청입니다.
5. 디자인이나 문구에 관련된 변경은 담당 팀원과 확인한 뒤 `main`에 합칩니다. 참여 인원이 적을 때 확인 방식은 팀 상황에 맞게 정합니다.

각 작업의 로컬 변경 사항이 GitHub에 올라갔는지 확인합니다. 현재 `main`에 합치거나 직접 푸시하면 공개 테스트 사이트에 자동 반영되며, 다른 브랜치의 미리보기 주소도 공개될 수 있습니다.

## 팀원에게 변경 내용을 전달할 때

- **무엇을 바꾸었나요?** 예: 샘플 리포트 목차의 동작을 수정했습니다.
- **왜 바꾸었나요?** 예: 원하는 샘플 구역을 쉽게 찾을 수 있도록 하기 위해서입니다.
- **어떻게 확인했나요?** 실행한 테스트와 직접 확인한 내용을 적습니다.
- **아직 안 되는 것은 무엇인가요?** 실제 참가자의 PostHog 측정, 이메일 저장, 결제처럼 남은 사항을 적습니다. 개발자의 로컬 테스트 이벤트는 별도로 전송할 수 있습니다.

실제 이메일, 기획안, 개인 API 키와 비밀번호는 코드·이슈·PR에 올리지 않습니다. 사람에게 보여줄 화면과 문구는 팀이 확인한 내용만 사용합니다.
