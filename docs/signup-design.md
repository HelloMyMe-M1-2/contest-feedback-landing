# 사전 신청: Google 스프레드시트 연결 설계

> 상태: **로컬의 가상 신청이 Google 시트에 저장됨**. Apps Script 웹 앱과 공유 비밀값을 설정하고 로컬 브라우저에서 저장 성공을 확인했습니다. Cloudflare 배포 환경 연결과 실제 참가자 수집은 아직 준비되지 않았습니다.

## 목표

팀원이 별도 관리자 화면이나 데이터베이스 도구 없이 개인 Google 계정에 만든 비공개 스프레드시트에서 신청을 확인합니다. 실험은 짧게 진행하며 무료 사용 범위 내에서 시작합니다. Apps Script와 Cloudflare에는 사용량 한도가 있으며 향후 변경될 수 있습니다.

**방문자 → 랜딩페이지 → Cloudflare 서버 함수 → Google Apps Script → 비공개 Google 스프레드시트**

Google 시트가 신청 목록의 유일한 저장소입니다. 기존 D1 초안과 Google Sheets API·서비스 계정 방식은 사용하지 않습니다. `db/schema.sql`은 이전 초안이며 현재 저장소가 아닙니다. Cloudflare는 랜딩페이지 제공과 서버 함수에 계속 사용합니다.

## 구성 요소와 역할

| 구성 요소 | 하는 일 |
| --- | --- |
| 랜딩페이지 | 이메일, 공모전 준비 단계(선택), 개인정보 동의를 받고 서버 함수에 전송 |
| Cloudflare 서버 함수 | 입력값과 동의를 다시 검사하고 Apps Script에 요청, 응답을 확인해 페이지에 결과 전달 |
| Apps Script | 요청 인증을 확인하고 정해진 시트의 `signups` 탭에 한 행 추가, 결과를 JSON으로 반환 |
| Google 스프레드시트 | 신청 시각, 이메일, 준비 단계, 동의 문구 버전을 보관. 권한을 받은 팀원이 직접 확인 |
| PostHog | 방문·샘플 확인·신청 시작·저장 성공을 행동 이벤트로만 기록. 이메일·입력값은 전송하지 않음 |

이미 만든 시트에는 `signups` 탭과 네 개의 열이 있습니다. 2026-11-20 확인 시 소유자에게만 공개돼 있었으며 팀원 공유는 아직 하지 않았습니다. 팀에서 신청자를 확인할 사람에게만 시트 접근 권한을 따로 부여합니다.

## 신청 흐름과 오류 처리

1. 방문자가 이메일을 입력하고 동의한 뒤 신청합니다. 선택 질문은 답하지 않아도 됩니다.
2. 서버는 필수값과 이메일 형식, 동의 여부, 선택지 허용값을 검사합니다. 이메일과 입력값을 URL, 분석 이벤트, 오류 로그에 넣지 않습니다.
3. 서버가 Apps Script에 신청 정보와 **서버 전용 공유 비밀값**을 POST 본문으로 전달합니다. Apps Script는 비밀값을 확인한 후 시트에 행을 추가하고 `{ "ok": true }`를 반환합니다. 시트에 쓰는 문자열은 수식으로 해석되지 않도록 문자로 처리합니다.
4. Apps Script 응답은 Google의 다른 주소로 리디렉션될 수 있으므로 서버에서 리디렉션과 응답 본문을 처리합니다. Cloudflare가 정상 HTTP 응답과 명시적인 성공 JSON을 모두 확인한 경우에만 폼에 성공을 반환합니다. **브라우저의 `no-cors` 응답이나 완료 화면 표시만으로 저장 성공을 판단하지 않습니다.**
5. 화면은 서버 성공을 확인했을 때만 신청 완료를 보여주고 `registration_completed`를 기록합니다. 오류·설정 누락·응답 형식 불일치 시 완료를 표시하지 않고 다시 시도할 수 있도록 안내합니다.
6. 저장 후 응답이 끊기면 실제 저장 여부를 화면에서 알 수 없습니다. 자동 재전송은 하지 않습니다. 방문자가 다시 신청하면 중복 행이 생길 수 있어 팀이 확인합니다. 첫 실험에서는 완전한 중복 방지를 약속하지 않습니다.

## 접근 관리와 개인정보

- Apps Script는 작성자 계정으로 실행하고 모든 사용자가 호출을 시도할 수 있는 웹 앱으로 배포했습니다. URL만으로 보호되지 않으며 비밀값이 일치하지 않으면 저장하지 않습니다.
- Apps Script의 공유 비밀값은 Script Properties, Cloudflare의 값은 서버 전용 Secret에 각각 저장합니다. 브라우저 코드·GitHub·채팅·URL에는 포함하지 않습니다. 비밀값을 Apps Script가 확인하기 전에는 요청을 처리하지 않습니다. 노출 시 두 곳에서 교체합니다.
- Cloudflare를 우회해 Apps Script 주소로 직접 요청할 수 있으므로, 서버의 출처 검사나 속도 제한만으로 직접 호출이 차단된다고 가정하지 않습니다. 공유 비밀값은 위험을 줄일 뿐 완전한 남용 방지를 보장하지 않습니다. 제한이나 장애가 생기면 수집을 중단하고 점검합니다.
- 필수 안내는 실제 수집 항목, 이용 목적, 보유·삭제 기준, 관리 담당자와 연락 방법, 필요한 국외 처리 정보를 팀이 확정한 내용에 맞춥니다. 원본 시안의 동의 문구는 운영 정책으로 확정된 것이 아닙니다. 시트 접근 권한과 삭제 요청 처리 담당자도 정합니다.
- 스프레드시트에 이메일을 넣으므로 팀원 공유는 필요한 사람에게만 합니다. PostHog 자동 수집·URL·IP 등 나머지 수집 경로는 운영 연결 전 별도 확인합니다.

## 최소 확인과 순서

1. 기존 개인 시트의 `signups` 탭을 사용하고 Apps Script를 연결합니다. 스크립트의 시트 접근 권한과 실행 주체를 확인합니다.
2. Apps Script의 수신 방식과 서버 비밀값을 설정하고 Cloudflare 서버 함수를 기존 서비스 계정 방식에서 교체합니다. Google Cloud 프로젝트를 별도로 직접 만들지 않는 방식을 우선하지만, Google 계정 정책 또는 Apps Script의 설정에 따라 추가 단계가 필요할 수 있습니다.
3. **가상의 이메일**로 신청해 시트의 한 행과 완료 화면이 일치하는지 확인한 뒤 테스트 행을 지웁니다.
4. 실패 응답을 모의해 저장되지 않을 때 신청 완료가 나오지 않는지 확인합니다. 저장 성공 후 응답이 끊기는 경우는 중복 가능성으로 안내합니다.
5. 팀이 접근 권한과 개인정보 안내를 정하고, 실제 참가자 수집과 PostHog 운영 연결은 별도로 준비합니다.

## 현재 구현과 남은 연결

- `functions/api/signup.js`: 같은 출처·입력·동의를 검사하고 Apps Script로 요청합니다. Google의 리디렉션은 `script.googleusercontent.com`만 허용하고 비밀값을 다시 보내지 않습니다. 성공 JSON만 신청 성공으로 처리합니다.
- `scripts/apps-script/Code.gs`: 비밀값·입력을 다시 검사하고 `signups` 탭에 기록합니다. 시트 수식으로 해석될 수 있는 이메일을 이스케이프하고 동시에 요청이 들어와도 행이 겹치지 않게 잠금을 사용합니다.
- 시트에 연결된 Apps Script 프로젝트와 로컬 `.dev.vars`에 필요한 값을 설정했습니다. 웹 앱은 배포했지만 Cloudflare의 운영 환경에는 아직 설정하지 않았습니다.
- 자동 테스트는 가짜 응답과 모의 시트로 성공·실패·잘못된 요청·리디렉션을 검사했습니다. 추가로 로컬 Node 테스트 서버에서 브라우저 → 동일한 신청 함수 → Apps Script → 실제 시트 저장과 완료 화면을 확인했고, 가상의 테스트 데이터 3행은 삭제했습니다. `signups` 헤더만 남았음을 확인했습니다. 신청 시각은 UTC ISO 형식입니다. 저장 후 응답이 끊기면 중복될 수 있습니다.
- 2026-11-20에는 Vite 개발 서버와 임시 로컬 Node 테스트 서버를 연결해 가상 신청을 다시 제출했습니다. 같은 신청이 시트에 저장되고 완료 화면이 표시됐으며, PostHog의 Activity에서 `registration_started`와 `registration_completed`가 도착한 것을 확인했습니다. 완료 이벤트에는 `test_environment: local`과 가상의 게시글 ID가 있었습니다. 시트의 테스트 행은 삭제했지만 PostHog 테스트 이벤트는 남아 있으므로 실제 결과와 구분해야 합니다. 이 검사는 Cloudflare 실행 환경을 사용한 검사가 아닙니다.

### 로컬에서 서버 함수 확인

개발자는 `npm install` 후 `npm run build`, `npm run dev:pages`를 실행합니다. 이 명령은 고정된 버전의 Wrangler를 npm을 통해 실행하며, 처음 실행할 때는 내려받기 위한 네트워크가 필요할 수 있습니다. Wrangler가 빌드된 화면과 Pages Function을 로컬에서 실행합니다. `npm run dev`의 Vite 개발 서버와는 다릅니다. 코드 수정 후에는 빌드를 다시 해야 합니다. 콘솔에 표시된 로컬 주소를 사용하고 실제 신청자 정보는 입력하지 않습니다.

서버 설정은 Git에 포함되지 않는 `.dev.vars`의 `SIGNUP_SCRIPT_URL`과 `SIGNUP_SHARED_SECRET`을 사용합니다. 동일한 비밀값은 Apps Script 스크립트 속성에 설정되어 있습니다. 이 작업 환경에서는 Wrangler가 파일 감시 오류와 내부 요청 오류를 보였고, 신청 요청이 503을 반환했습니다. 반면 같은 함수를 별도 로컬 Node 서버에서 실행하면 시트 저장에 성공했습니다. Wrangler 오류의 정확한 원인은 아직 확인하지 못했으며 Cloudflare 실제 배포 환경에서의 동작은 검증되지 않았습니다. 로컬 테스트가 성공하더라도 Cloudflare에 배포된 것은 아닙니다.

2026-11-21 추가 진단에서는 신청 코드를 사용하지 않은 최소 Cloudflare Worker의 외부 요청도 내부 오류를 반환했습니다. 같은 환경에서 Node의 같은 주소 요청은 응답했습니다. 또한 로컬 Worker에서 Google 응답을 가짜로 대체해 실제 신청 함수를 호출했을 때 정상 입력은 201, 다른 출처는 403, 잘못된 이메일은 400을 반환했습니다. 이는 입력 검사와 응답 처리가 로컬 Worker에서 작동한다는 제한된 확인이며, 실제 Google 요청이나 배포 환경의 성공을 증명하지 않습니다.

### 연결 준비 순서

1. Apps Script 프로젝트 설정의 스크립트 속성에 `SIGNUP_SHARED_SECRET`을 설정했습니다. 임의로 생성한 충분히 긴 비밀값을 쓰고, 코드·GitHub·채팅이나 URL에 적지 않습니다. `SPREADSHEET_ID`는 기존 시트 ID로 설정되어 있습니다.
2. 웹 앱은 **실행 사용자: 나**, **액세스: 모든 사용자**로 배포되어 있습니다. 이는 웹 앱 URL을 아는 사람이 요청을 시도할 수 있다는 뜻이며, 시트 자체를 공개한다는 뜻은 아닙니다. 비밀값이 맞는 요청만 저장하도록 만들었지만 악용을 완전히 막지는 못합니다.
3. Google 권한 승인 화면에서 범위를 확인합니다. `SpreadsheetApp.openById`는 Google 문서상 스프레드시트 읽기·쓰기 권한을 요청할 수 있습니다. 코드가 특정 시트만 사용하도록 작성됐어도 Google 계정 권한 자체가 그 파일 하나로만 제한된다고 가정하지 않습니다. 웹 앱 실행 시 연결 문서의 활성 시트를 가져오는 방식은 사용할 수 없어 ID로 엽니다. [Google 권한 안내](https://developers.google.com/apps-script/reference/spreadsheet/spreadsheet-app#openbyidid), [바운드 스크립트의 웹 앱 제약](https://developers.google.com/apps-script/guides/bound#special_methods)
4. Cloudflare Pages의 **서버 전용** 환경 변수 또는 Secret에 `SIGNUP_SCRIPT_URL`(배포 URL)과 `SIGNUP_SHARED_SECRET`(Apps Script와 같은 값)을 설정합니다. `VITE_` 변수에 넣지 않습니다. 로컬 `.dev.vars`도 Git에서 제외되어야 합니다.
5. Cloudflare와 실제 웹 앱이 연결된 테스트 환경에서 가상의 이메일로 한 행 저장·성공 화면·PostHog 테스트 이벤트를 확인합니다. 실패 시 성공으로 표시되지 않는지도 확인합니다. 테스트 행 처리, 팀 접근 권한, 개인정보 고지·동의, 서비스 준비 상태는 실제 수집 전에 점검합니다.

개인 키나 실제 신청자 데이터는 저장소에 넣지 않습니다. 앱과 시트의 실제 배포·인증·연결 완료 전에는 코드를 GitHub에 올리는 것만으로 이메일 수집이 시작되지 않습니다.
