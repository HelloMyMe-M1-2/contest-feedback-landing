# 화면과 PostHog가 바뀔 때의 측정 기준

> 2026-11-17 검토 기록. 현재 실제 참가자 측정은 연결되지 않았습니다. 이 문서는 지금 확인한 사실과 앞으로 구현할 기준을 구분합니다. 디자인을 바꿔도 수치가 자동으로 같아지거나, PostHog가 바뀌어도 수정이 필요 없다고 보장하지는 않습니다.

## 팀원이 먼저 볼 내용

사이트의 문구나 버튼 위치는 바꿀 수 있습니다. 다만 **우리가 무엇을 하나의 행동으로 셀 것인지**는 디자인과 별도로 정하고, 변경 전후에 같은 기준인지 확인해야 합니다. 예를 들어 구매 버튼을 상단으로 옮겨도 실제로 버튼을 누른 횟수는 계속 `purchase_clicked`로 기록할 수 있습니다. 하지만 구매 가격이 생기거나 버튼이 다른 행동을 하게 된다면 결과를 같은 조건으로 비교하면 안 됩니다.

PostHog에서 보고 싶은 숫자가 추가되거나 사용하는 도구가 변경되어도, 사이트의 행동 정의와 전송 방식을 구분하면 필요한 부분을 좁혀 수정할 수 있습니다. 다만 기존 코드가 **어떤 변경이든 자동으로 처리하는 것은 아닙니다.**

| 바뀌는 것 | 우리가 할 일 |
| --- | --- |
| 글자·색상만 바뀜 | 같은 행동을 같은 기준으로 기록하는지 확인 |
| 버튼·예시의 위치나 크기가 바뀜 | 클릭뿐 아니라 예시 노출과 스크롤 기준을 다시 확인 |
| 가격·제공 내용이 바뀜 | 구매 제안 버전을 바꾸고 결과를 나누어 해석 |
| 새로 보고 싶은 행동이 생김 | 어떤 행동인지와 언제 기록할지 먼저 정하고 코드·명세·테스트를 함께 변경 |
| PostHog 설정이나 도구가 바뀜 | 실제 전송 정보와 대시보드 기준을 검증. 서비스 화면은 측정 실패와 별개로 작동해야 함 |

## 이번에 확인한 결과

| 검토 항목 | 현재 상태와 위험 | 조치 |
| --- | --- | --- |
| 행동 이름과 화면 문구 | `purchase_clicked` 등은 버튼의 CSS나 표시 문구가 아니라 행동 이름을 사용합니다. 다만 React 화면에서 직접 기록을 호출하므로 버튼을 교체할 때 연결이 빠질 수 있습니다. | 화면 변경 시 행동 연결을 검증하는 절차를 아래에 정의했습니다. 자동 보장은 아닙니다. |
| 스크롤의 끝점 | 구매 영역이 페이지의 끝으로 지정되어 있어 해당 영역을 위로 옮기면 이후 콘텐츠가 제외될 수 있었습니다. | 로컬 실습에서 구매 영역 대신 `data-analytics-content`로 감싼 전체 콘텐츠의 끝을 보도록 수정했습니다. 새 섹션도 이 영역 안에 있어야 합니다. |
| 측정 실패와 화면 동작 | 기록 도구가 오류를 던지면 구매 안내가 표시되기 전에 클릭 처리가 중단될 수 있었습니다. | 현재 동기식 이벤트 기록 오류를 잡고 화면 처리를 계속하도록 수정했습니다. 로컬 테스트 SDK 초기화에 실패해도 화면을 표시합니다. 네트워크 전송 성공까지 보장하는 것은 아닙니다. |
| 예시·구매 영역 노출 | 현재는 해당 요소의 50% 이상이 2초 동안 보일 때 노출로 기록합니다. 아주 긴 요소는 작은 화면에서 50%가 동시에 보이지 않을 수 있습니다. 레이아웃·화면 크기에 따라서도 결과가 달라집니다. | 기존 테스트 기준은 유지합니다. 최종 디자인에서 측정할 요소와 노출 기준을 다시 결정하고 모바일에서 검증해야 합니다. |
| 예시 ID와 제안 버전 | 예시 ID는 현재 세 종류로 코드에 정해져 있고 예시·구매 제안의 버전도 화면 코드에 직접 들어 있습니다. 내용만 바꾸어도 버전이 자동 변경되지 않습니다. | 내용 추가·수정 시 ID와 버전을 함께 관리하는 절차를 정했습니다. 데이터로 분리하거나 자동화하는 것은 아직 구현하지 않았습니다. |
| 새 이벤트의 PostHog 허용 | 이벤트 이름과 전송 허용 목록이 따로 있어 새 이벤트가 실습에는 보여도 PostHog 테스트에서는 빠질 수 있었습니다. | `EventProperties`에 이벤트를 추가하면 테스트 전송 허용 여부를 코드에서 명시해야 타입 검사를 통과하도록 했습니다. |
| PostHog에 보낼 속성 | 테스트용 허용 목록에 없는 속성은 전송 전에 제거합니다. 반대로 허용 목록 변경은 개인정보 검토가 필요합니다. | 계약의 이벤트별 속성이 바뀌면 로컬 테스트 전송 허용 여부를 각각 명시하도록 했습니다. 실제 전송과 속성 값의 안전성을 자동 보장하지 않으며, 운영 수집 정책도 아닙니다. |
| PostHog SDK 교체·업데이트 | SDK의 기본값이나 필수 필드가 바뀌면 필터, 이벤트 전송이나 대시보드가 달라질 수 있습니다. 코드의 타입 선언만으로 실제 네트워크 결과를 보장하지 못합니다. | 버전을 고정하고 업데이트 검증 및 되돌리기 절차를 정했습니다. 실제 새 버전 검증은 아직 하지 않았습니다. |
| 중복·누락·시간 | 이벤트마다 별도의 중복 제거용 ID가 없고 전송 성공은 보장되지 않습니다. 로컬 이벤트의 `occurred_at`은 현재 PostHog 사용자 속성으로 전달하지 않습니다. | 클릭 횟수와 페이지 방문 수를 분리하고, 중복 제거·시간 기준을 실험 전 별도 설계하도록 기록했습니다. 임의 재전송이나 무손실을 약속하지 않습니다. |

## 변하지 않아야 할 행동의 뜻

상세 이름·속성·현재 발생 조건은 [이벤트 명세](events.md)를 기준으로 합니다. 여기서 버전은 서로 다른 것을 구분합니다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 행동 이름 | 사용자가 무엇을 했는지 | `purchase_clicked`: 구매 버튼 선택. 실제 결제 아님 |
| 측정 규칙 | 언제 한 건을 기록하는지 | 예시 노출은 현재 요소 50%·2초 이상 |
| 이벤트 스키마 버전 | 이름과 속성 등 기록 형식의 버전 | 현재 **로컬 테스트**는 `event_schema_version: 2` |
| 콘텐츠·제안 버전 | 사용자가 본 예시 또는 구매 조건의 버전 | `example_version`, `offer_version`; 현재 코드에서는 수동 지정 |
| 실행 환경 | 테스트 기록과 실제 실험 기록의 구분 | 현재 테스트는 `test_environment: local`. 실험용 값과 구현은 미정 |

**화면 문구를 이벤트 이름이나 ID로 사용하지 않습니다.** 같은 의미의 버튼이 여러 위치에 있다면 이름은 같게 유지할 수 있습니다. 위치별 비교가 필요하면 팀이 정한 제한된 위치 ID를 별도 속성으로 설계하되, 아직 구현된 기능은 아닙니다. 같은 사람의 반복 클릭과 여러 사람의 클릭을 구분하려면 이벤트 건수와 `page_view_id` 기준 행동한 페이지 수를 각각 봅니다. 페이지 ID로 실제 사람이나 다른 기기의 방문을 하나로 확정할 수는 없습니다.

`example_selected`는 **선택**, `example_exposed`는 정해진 조건의 **노출**입니다. 처음부터 표시된 예시를 보더라도 별도로 선택하지 않았다면 선택 이벤트가 없을 수 있습니다. 구매 조건 노출과 구매 클릭도 별개이며, 2초 전에 클릭하면 노출 이벤트 없이 클릭이 생길 수 있습니다. 노출 후 클릭 비율과 전체 방문 대비 클릭 비율을 구분합니다.

### 변경 유형에 따른 버전 관리

1. 색상이나 문구만 바뀌어도 사용자의 이해·행동이 달라질 수 있습니다. 기술적으로 같은 이벤트가 발생하더라도 중요한 실험 문구나 예시의 변화는 팀 기록에 남기고, 내용이 달라지면 콘텐츠 버전을 바꿉니다.
2. 가격, 제공 범위 등 구매 판단에 영향을 주는 제안이 바뀌면 `offer_version`을 바꾸고 기간과 내용을 기록합니다. 현 코드는 버전을 자동 갱신하지 않으므로 직접 수정·검증해야 합니다.
3. 속성을 추가할 때는 기존 이벤트의 의미와 과거 데이터가 유지되는지 확인하고, 스키마 버전과 테스트·전송 허용 목록·분석 필터에 반영합니다. 과거 기록에 새 속성이 생긴다고 가정하지 않습니다.
4. 발생 조건이나 의미가 호환되지 않게 바뀌면 **새 이벤트 이름 또는 새 측정 규칙 버전**을 정하고 이전 데이터와 분리합니다. 예를 들어 노출 기준을 50%·2초에서 다른 기준으로 바꾸면 버전 없이 같은 지표로 합치지 않습니다. 어떤 방식을 쓸지는 변경 시 이벤트 명세에 기록합니다.
5. 측정 대상이나 디자인 자체가 바뀌면 같은 이름이라도 행동 확률과 전환율이 바뀔 수 있습니다. 콘텐츠·제안 버전, 화면 변경 시점, 기기별 결과와 관측 기간을 함께 봅니다.

## 개발자를 위한 책임 경계

```text
사용자 행동 / 화면 관찰
    → 행동 이름과 속성 정의
    → 기록 계층
    → PostHog 테스트 전송 정책과 SDK
    → PostHog 저장·분석
```

| 책임 | 현재 코드 | 변경할 때 확인할 점 |
| --- | --- | --- |
| 화면과 행동 연결 | `src/App.tsx`, `src/components/ExamplePreview.tsx` | 디자인 교체 후 클릭·노출 호출, 콘텐츠 영역, 모바일·키보드 동작 |
| 행동의 이름과 형식 | `src/analytics/contracts.ts`, `docs/events.md` | 정의·속성·중복 기준·버전·분자와 분모 |
| 기록 전달 경계 | `src/analytics/tracker.ts` | 화면이 특정 분석 도구 세부사항에 의존하지 않도록 유지. 현재는 동기식 오류만 격리 |
| 로컬 PostHog 변환·허용 목록 | `src/analytics/posthogTest.ts`, `src/analytics/posthogTestPolicy.ts` | 이벤트별 허용 여부, 속성 목록, 개인정보 차단과 SDK 호환성 |
| 로컬 화면 관찰 | `src/analytics/useExposure.ts`, `src/analytics/usePageMetrics.ts` | 관찰 대상, 화면 전환·재마운트, 콘텐츠 범위와 깊이 계산 |
| 자동 검사 | `tests/analytics.test.mjs` | 이벤트 전송 정책, 실패 시 화면 흐름, 시간·스크롤 계산. 현재 브라우저 전체 동작을 검증하지는 않음 |

PostHog의 대시보드 설정만 바꿔서는 사이트에서 새 이벤트나 속성이 자동으로 만들어지지 않습니다. 반대로 사이트에 새 이벤트를 추가하더라도 테스트용 허용 정책과 분석 보고서를 함께 확인해야 합니다. 현재 테스트 전송 정책은 승인하지 않은 이름과 속성을 차단하며, 변경된 SDK가 요구하는 정보까지 빠질 가능성이 있으므로 **실제 요청과 PostHog 도착 결과를 검증**해야 합니다.

## 화면·이벤트 변경 절차

1. **변경 내용 기록:** 문구만 바꾸는지, 행동의 뜻·노출 조건·가격·예시 내용까지 바꾸는지 적습니다. 조건이 달라지면 결과를 비교할 기간과 버전도 정합니다.
2. **명세 먼저 수정:** [이벤트 명세](events.md)에 이름, 발생 시점, 속성, 페이지 방문당 중복 기준과 지표 분자·분모를 적습니다. 새 속성은 허용할 값과 목적을 정하고 이메일·입력값은 넣지 않습니다.
3. **화면 연결과 정책 변경:** 관련 화면의 행동 연결을 수정합니다. 전체 콘텐츠는 `data-analytics-content` 안에 두고 실습장은 그 밖에 둡니다. PostHog 테스트 정책에서 새 이벤트와 속성의 전송 허용 여부를 각각 명시합니다. 공통 속성 및 SDK 필드 변경은 별도로 검토합니다.
4. **자동 검사:** `npm test`와 `npm run build`를 실행합니다. 추가·변경한 행동과 속성이 전송 경계까지 유지되는지, 측정 도구가 실패해도 화면이 작동하는지 의미 있는 테스트를 추가합니다. 이 검사만으로 실제 브라우저와 PostHog 도착은 증명되지 않습니다.
5. **브라우저 검증:** 가상 데이터로 화면을 열어 모바일·데스크톱, 키보드, 반복 클릭, 긴 콘텐츠, 예시 선택·재선택, 탭 전환, 새로고침을 확인합니다. 버튼을 위아래로 옮기거나 콘텐츠를 추가해도 콘텐츠 끝과 이벤트 대상이 맞는지 점검합니다. 브라우저 검증은 이후 최종 디자인에 대해 다시 해야 합니다.
6. **PostHog 테스트 검증:** 별도 설정한 로컬 테스트에서 허용된 이벤트와 속성이 도착하는지, 의도하지 않은 이벤트·URL·입력값이 빠졌는지 확인합니다. 가상의 값만 사용하고, 테스트 구분값과 대시보드 필터를 함께 확인합니다. 현재 테스트값은 실제 실험 데이터가 아닙니다.
7. **기록 공유:** 변경 내용과 버전, 테스트 결과, 아직 미확인인 부분을 기록하고 관련 팀원에게 전달합니다. 비교가 어려운 구간이 생기면 분석에도 표시합니다.

| 변경 사례 | 확인할 내용 |
| --- | --- |
| 보고서에 기존 속성을 추가해 보고 싶음 | 현재 이벤트에 실제로 존재하는지, 해당 환경·기간의 값인지 확인. 대시보드만 바꾸면 되는지, 사이트 변경도 필요한지 구분 |
| 새 속성이나 이벤트가 필요함 | 위 변경 절차에 따라 허용 값과 의미를 정의. 이벤트 목록뿐 아니라 전송 속성 목록과 가상 데이터 테스트까지 변경 |
| SDK 버전·기본값 변경 | `package.json`과 잠금 파일을 함께 갱신. 공식 문서의 변경점, 자동 수집, 전송 필드, 식별자·쿠키·IP·URL, 세션 녹화와 요청 호스트를 확인 |
| SDK 이벤트 형식이나 필수 속성이 바뀜 | 테스트 필터가 필요한 필드를 제거하지 않는지, 새 필드가 개인정보를 포함하지 않는지 확인. 전송 결과와 PostHog 저장 결과를 모두 검증 |
| 전송 실패·차단 | 화면 동작을 유지하고 로컬에서 오류를 확인. SDK 재시도나 분석 누락을 무손실·정확히 한 번 전송으로 가정하지 않음 |
| 분석 도구 변경 | 행동 명세와 화면 정의를 유지하되 새로운 전송 어댑터·개인정보 처리·집계 기준을 별도 검증. 현재 구조가 도구 교체를 자동으로 끝내주지는 않음 |

현재 `posthog-js` 버전은 프로젝트의 `package.json`과 잠금 파일에 고정되어 있습니다. SDK 업데이트 시에는 기존 버전을 복원할 수 있도록 변경 전 파일과 비교하고, 테스트 데이터로 확인한 결과를 남깁니다. 기존 PostHog 이벤트와 새 이벤트의 의미가 다르면 대시보드에서 무작정 합치지 않습니다. PostHog의 SDK 설정과 데이터 처리 방식은 바뀔 수 있으므로 작업 시점의 [공식 SDK 문서](https://posthog.com/docs/libraries/js)와 [이벤트 수집 문서](https://posthog.com/docs/product-analytics/capture-events)를 다시 확인합니다.

## 실제 실험 전 아직 필요한 일

- 실제 분석 전송 구현, 실행 환경 구분, 허용된 게시글 ID 관리, 테스트 데이터와 실험 데이터 분리 및 보고서 검증
- 현재 로컬 이벤트·속성 허용 목록과 별개의 **실험용** 수집 정책과 런타임 값 검증. 현 TypeScript 타입과 URL의 형식 검사만으로 개인정보 유입을 막을 수 없음
- 실제 화면 기준의 예시·구매 제안 ID와 버전 관리, 콘텐츠 범위와 노출 기준 확정
- 브라우저에서 화면 바꾸기·재마운트·비동기 SDK 오류·차단·재시도·강제 종료를 포함한 통합 검증. 현재 동기식 오류 처리와 단위 테스트만으로 모두 보장하지 않음
- 이벤트의 발생 시간과 수신 시간, 중복 제거·재시도 정책, 누락을 어떻게 해석할지 결정. 추가 식별자는 필요한 범위와 보관 조건을 함께 검토
- PostHog의 자동 수집, 식별자·쿠키, IP·URL, 국외 처리, 고지·필요한 동의, 접근·보관·삭제 검토. 설정 변경 전 테스트 데이터의 처리도 별도 결정

현재 이 항목들은 **검토 및 구현 대기**입니다. 실제 사용자 측정, 이메일 수집, 결제 또는 배포가 완료되었다는 뜻이 아닙니다.
