# 실험 준비와 확인 순서

이 문서는 **아직 실제 참가자를 받지 않는 준비 단계**의 작업 순서입니다. 팀이 전달한 화면은 그대로 유지합니다. 서버에 코드가 준비돼 있는 것, 테스트가 성공한 것, 실제 참가자를 받는 것은 서로 다른 상태입니다.

## 지금 확인된 것

| 구분 | 확인 결과 | 아직 확인할 것 |
| --- | --- | --- |
| 사전 신청 화면과 시트 | 가상 이메일로 Cloudflare 배포 화면에서 시트 저장과 완료 화면 확인 후 테스트 행 삭제·접수 중단 | 실제 접수 전 설정 복원과 개인정보 안내 확인 |
| 신청 함수의 실행 | 배포 환경에서 실제 Google과 통신 성공, 접수 차단 후 이전 배포에서도 저장 실패 확인 | 로컬 Wrangler 외부 요청 오류의 원인 |
| PostHog | 로컬과 배포 가상 신청의 시작·완료 이벤트 도착 확인. `local` / `preview`로 구분 | 실제 참가자 측정 코드는 미구현. 운영에서 개인정보 설정과 이벤트 도착 확인 필요 |
| 사이트 | Cloudflare Pages의 공개 테스트 주소 배포 완료. 현재 시트와는 연결되지 않아 신청을 저장하지 못함 | 실제 참가자 수집 전 서버 연결과 측정·개인정보 설정 검증 |

Cloudflare Pages의 미리보기 주소도 기본적으로 공개입니다. 현재 테스트 주소는 누구나 열 수 있으며 GitHub `main`의 변경이 자동 배포됩니다. 팀 내부 확인을 위한 제한이 필요하면 별도로 설정해야 합니다. [Cloudflare 미리보기 안내](https://developers.cloudflare.com/pages/configuration/preview-deployments/)

## Cloudflare 연결을 확인할 때

1. **접근 범위 확인:** 테스트 배포가 외부에서 열릴 수 있는지 먼저 확인합니다. 실험 시작 전에는 실제 신청자의 이메일을 입력하지 않습니다.
2. **환경 변수 설정:** Cloudflare 서버 전용 설정에 `SIGNUP_SCRIPT_URL`과 `SIGNUP_SHARED_SECRET`을 넣습니다. 두 값은 현재 사용자만 가진 설정에서 확인하며, 문서·채팅·스크린샷·GitHub에 적지 않습니다. `VITE_` 접두사를 붙이지 않습니다.
3. **가상 신청:** 테스트용 이메일로 신청한 다음 성공 화면과 시트의 새 행을 각각 확인합니다. 테스트 행만 지웁니다.
4. **실패 확인:** 설정 오류나 저장 실패에 성공 화면이 나오지 않는지 별도 테스트합니다. 원래 설정을 잃지 않도록 확인할 환경과 복구 방법을 먼저 정합니다.
5. **기록:** 확인 날짜, 테스트한 환경, 결과와 남은 오류를 [사전 신청 설계](signup-design.md)에 남깁니다. 로컬에서 성공한 결과를 Cloudflare 배포 성공으로 기록하지 않습니다.

### 현재 로컬 오류

2026-11-21 이 작업 환경에서는 Wrangler 로컬 실행기의 외부 요청이 실패했습니다. 신청 코드가 없는 별도 최소 테스트도 외부 요청에서 내부 오류가 났고, 같은 주소에 대한 Node 요청은 응답했습니다. 로컬 실행기에서 Google 응답을 가짜로 대체하면 신청 함수는 성공 응답과 잘못된 요청 거부를 처리했습니다. 신청 함수의 입력·응답 처리는 일부 확인했으며, 로컬 외부 연결 실패의 정확한 원인은 아직 모릅니다. 이후 실제 Cloudflare 배포 환경에서는 Google 시트 저장에 성공했습니다.

## PostHog 실험 측정 준비

현재 개발자 테스트용 측정만 구현되어 있습니다. 기본 공개 주소는 이벤트를 전송하지 않습니다. 배포 테스트는 별도 빌드 설정과 전용 쿼리에서만 켜지며 수신을 확인했습니다. 실제 측정을 사용하려면 아래 작업을 구현하고 검증해야 합니다.

1. **수집 기준:** [이벤트 명세](events.md)의 방문·샘플·신청·체류시간 등을 기준으로 실제로 필요한 이벤트를 확정합니다. 현재 화면에 없는 구매 버튼의 이벤트는 발생하지 않습니다.
2. **유입 식별:** 게시글마다 개인 정보가 없는 ID를 정하고 팀이 ID와 게시글의 대응표를 관리합니다. URL에서 받은 값을 그대로 신뢰하지 않고 허용한 ID만 전송하도록 운영용 코드를 만듭니다. 누락·미등록 값은 `unknown`으로 처리합니다.
3. **수집 설정:** 이메일과 폼 답변은 시트에만 보관하고 PostHog 이벤트에 보내지 않습니다. 자동 수집·세션 녹화·URL·referrer·IP·식별자와 국외 처리, 필요한 고지·동의 및 보관·삭제 기준을 확인한 뒤 운영 전송을 구현합니다. 쿠키를 사용하지 않거나 IP 저장을 끄더라도 모든 개인정보 처리가 없어지는 것은 아닙니다.
4. **테스트 분리:** 테스트와 실제 실험을 이벤트 속성으로 구분하고 대시보드·퍼널의 모든 단계에 같은 조건을 적용해 확인합니다. 현재 테스트의 `test_environment: local`은 실험 데이터가 아닙니다.
5. **도착 확인:** 테스트 환경에서 각 행동을 실행해 PostHog에 허용한 이벤트와 속성만 도착하는지, 이메일·입력값·불필요한 URL이 없는지 확인합니다. 이벤트 차단이나 페이지 종료로 기록이 누락될 수 있습니다.
6. **보고서:** [대시보드 안내](posthog-dashboard.md)에 따라 페이지 방문 기준 수치를 확인합니다. PostHog 기본 퍼널의 사용자 단위와 페이지 방문 단위는 다릅니다. 게시글 조회 수와 랜딩 이전 링크 클릭은 PostHog가 알 수 없어 별도로 확인해야 합니다.

배포 테스트에서 확인한 `registration_completed`는 신청 저장 성공 응답을 기준으로 한 행동 이벤트입니다. 시트의 신청자 수와 전송 실패·중복 등으로 다를 수 있으며, `result: new`는 고유 신청자라는 뜻이 아닙니다.

## 실제 신청 접수 전에 팀이 확인할 것

- 시트에 접근할 팀원과 권한, 신청자 문의·삭제 담당자.
- 화면의 개인정보 안내가 실제 수집 목적·보관·삭제와 일치하는지. 문구는 팀의 원본을 보존하고, 필요한 수정은 팀과 결정합니다.
- 시안에서 설명하는 서비스 내용과 실제 제공 상태를 참가자가 혼동하지 않는지.
- 실험 기간과 게시글별 ID, 테스트 데이터를 결과에서 제외하는 방법.

팀원 권한 초대는 담당자가 진행합니다. 현재 시트는 팀 전체에 공유된 상태가 아닙니다.
